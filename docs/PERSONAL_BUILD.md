# Melodia Personal 的构建与后续更新

本次个人修改保留在 `personal/local-first-search` 功能分支中：恢复原版安卓搜索页（含热搜首曲与热搜榜），音乐推荐/最新独立为底部“音乐”页，“你的偏好”旁增加搜索入口。在线歌曲优先使用已有本地音频；在“设置 → 本地与网易云匹配”集中管理歌曲批量匹配、专辑批量自动查找与核验及双向专辑对应，本地首页已移除匹配卡片。手动双向歌曲关联和 JSON 备份继续保留，专辑对应关系和专辑报告暂不包含在歌曲备份 JSON 中。关联存储与批量报告独立于官方 Room 曲库和下载记录，便于后续合并；合并时仍需检查冲突、测试和构建，不能保证未来任意版本无需调整。

当前个人版本为 `2.0.0-beta.19`（`versionCode=2000019`），另保留之前的个人版本。仍以官方提交 `c79ff932b616465ff42296781fe07002fdbfddb5` 为代码基线；个人版本号不表示已经包含未来官方同名版本的源码。沿用个人签名及应用 ID，新版用于覆盖升级已有个人版并保留数据。安装到手机后仍应实际检查本地授权、原有关联和播放。

## beta.19 的导入结果滚动边界修复

导入匹配结果列表触底后，消耗未被列表使用的向上拖动与惯性，避免交给已展开弹层反复执行回弹。正常列表惯性滚动仍由列表处理，向下拖动仍可关闭弹层。修复仅位于导入 UI，不修改匹配、目标歌单写入、播放或已有本地关联数据。

## beta.18 的文本导入、双向识别和目标歌单选择

TXT 歌单导入面板增加“粘贴文本”，无需先保存文件。同一文本可混用“歌名 - 歌手”和“歌手 - 歌名”，也支持不带空格的横线。沿用原有预览、待处理选择、私密歌单和失败重试；两种顺序或分隔位置均匹配不同歌曲时不自动选择。未自动匹配的条目会对调词序补查一次，合并结果后核对，沿用原有并发和超时限制。文件和文本共用同一个解析、匹配与写入流程，不更改已有匹配数据或播放逻辑。详见 [TXT / 文本歌单导入](TXT_PLAYLIST_IMPORT.md)。

匹配后可选择导入到已有歌单，或新建并填写歌单名称。目标列表复用官方用户歌单仓储；已有歌单先以服务器详情核对所有者和当前歌曲，仅追加缺失项，沿用同一个目标重试。新建歌单继续支持私密开关，导入前仅预览不写入。

## beta.17 的封面歌词快捷入口

歌曲播放详情页点击当前专辑封面，直接打开原“显示歌词”的全屏歌词覆盖层，返回后回到播放详情页。竖屏、侧栏和横屏布局共用该入口；封面左右滑动仍切歌，封面外的留白不触发点击。播客封面维持原有行为。此版本未修改音量、音频焦点、播放引擎或数据库，保留 beta.16 的 TXT 导入和既有本地匹配、严格换源功能。

## beta.16 的听歌识曲入口与 TXT 歌单导入

独立音乐页在搜索按钮右侧新增听歌识曲音符，复用原搜索页的全局识别面板与权限流程。音乐库右上角＋改为“新建歌单／导入歌单（TXT）”菜单；TXT 逐行匹配、预览、勾选并确认后创建网易云歌单，默认私密。错误行和重复行单独标记，待处理项可重新搜索、直接点选。重试只核对服务器当前曲目，不依赖离线歌单缓存。详见 [TXT 歌单导入](TXT_PLAYLIST_IMPORT.md)。本次不改曲库 schema、原音频文件、已有本地匹配或播放源解析。

## beta.15 的严格换源与主页布局

主页中的音乐／最新等页面恢复官方布局，独立音乐底栏和其搜索入口继续保留。严格换源模式位于“设置 → 音源设置”，默认关闭；开启后跳过旧的在线换源缓存，并要求有可信预览及音频片段身份核对，不确定时拒绝该候选。保留本地文件、手动关联和下载优先的流程。片段核对不能证明远端整首内容绝对一致。

## beta.14 的多作者合辑分组修复

补上 SAF 文档导入没有文件路径时的目录证据，并处理系统把曲目作者代入专辑作者的情况。目录名称支持标点、方括号附注与专辑名前缀差异。展示、专辑匹配及保存时使用同一分组身份；`50 Classical Masterworks` 应显示为包含 50 首曲目的一张专辑，歌曲作者仍分别保留。没有数据库迁移、原音频标签写入、新依赖或新权限。

## beta.13 的本地专辑识别修复

保留与父文件夹同名的有效专辑标签，避免正常按专辑整理的音乐被误分为“未知专辑”。没有“专辑艺术家”标签的多演奏者合辑，仅在同一专用目录内专辑标签一致时按目录聚合；不同目录或平铺目录中的同名专辑不会因此合并。普通单歌手及有明确专辑艺术家标签的专辑继续使用原来的标识；不修改音频标签或数据库结构。升级后在“本地与网易云匹配 → 歌曲批量匹配与待处理”中刷新曲库即可重新识别，无需重建已有歌曲关联。

系统扫描未识别 WAV 内嵌 ID3 时，复用已有 TagLib 读取真实标题、歌手、专辑及封面。扫描、导入、关联文件校验使用一致的元数据；刷新时也补读已有导入 WAV 的标签，并保留其引用、来源、歌曲 ID 与日期。没有新增依赖、权限或标签写入。验证样本覆盖 `50 Classical Masterworks`、《原始人爱空调协会》《油漆匠》和《妈妈一起飞吧，妈妈一起摇滚吧》，具体安装与真实文件结果由 beta.13 最终验证记录提供。

## beta.12 的修复与维护整理

歌曲报告主按钮固定承担自动匹配，按状态显示“开始自动匹配／继续自动匹配／暂停自动匹配”；“人工核验 · 连续处理”是另一个独立按钮，避免已有报告时找不到创建自动匹配的入口。按钮区支持换行；进入人工处理会先暂停自动任务。

专辑批量报告的成功分类改为“已完成”。人工确认成功可以完成一张专辑，无需要求每首歌曲都已关联；同时保留真实歌曲关联数量，例如“已完成 · 歌曲 8/12 已关联”。确认使用本地专辑内容指纹和当前在线专辑范围，保存成功后跨重启保留，后续批量跳过。预览、暂停或失败不会新增确认。本地内容变化、更换专辑或解除对应会使原确认不再适用；已有歌曲引用仍按实际记录保留。旧版缓存没有可靠人工确认标志，升级后不推定旧的部分匹配专辑已经人工核验。操作说明见 [本地音频与匹配](LOCAL_AUDIO_PRIORITY.md)。

歌曲报告改为逐条容错解码，单条损坏不再使整份报告打不开；刷新时用当前曲库和实际确认引用恢复受影响条目。暂停共用有最终释放步骤的流程，即使进度写入失败也不会一直阻止下一次开始。两种手动选文件入口共用引用替换事务，保存前重新核对物理文件；播放解析完成前再次读取用户选择，避免较慢的自动查询覆盖刚刚更换的手动音源或开关。

离线可播放索引通过 `core.localmusic.LocalMusicApi` 查询本地源，不再从 `core` 直接依赖 `feature/localmusic` 的 Repository。歌曲、专辑和报告继续独立存储，不改官方 Room schema、下载表或现有歌曲备份格式。专辑核验标记为可选字段，旧 JSON 和未知字段均可兼容读取；专辑缓存解码移到后台，减少核验时主线程负担。

歌手专辑筛选同时修正两处逻辑：同一作品有多个发行版时，先选择满足最低曲数的发行版，再进行合并显示；重新选择同一资料库歌手时，会恢复此前被选择器取消的目录读取。MusicBrainz 请求标识使用实际构建版本和项目联系地址，便于独立上游功能包维护。

个人分支已完成与官方 CI 对齐的本地验证：Android、shared、desktop 单元测试、桌面编译及 Android Release 构建。具体测试数量、安装与运行验证由该版本最终验证记录列出；本地构建通过不代表 GitHub 工作流已运行，也不代替手机实际验收。

已按官方功能模板准备“歌手主要录音室专辑筛选”和“本地歌曲与专辑匹配”两份独立上游 PR 的源码、补丁与正文，尚未向官方仓库提交。两份功能包从同一官方基线构造，排除个人应用 ID、签名、更新仓库和音乐底栏等个人变化。请按 [上游 PR 准备说明](UPSTREAM_PR_PREPARATION.md) 审阅各自独立构建结果后，再从最新官方基线创建功能分支；不要把整个个人分支直接当作任一功能 PR。

## Fork、官方更新和应用内更新是三件事

- Fork 不会自动同步 `rinchao0721/Melodia` 的后续源码提交，也不会自动复制官方 GitHub Releases 或资产。
- 新增的 `Personal Android APK` 工作流只响应手动运行，不会自动同步上游、创建 tag 或发布 Release。
- 个人包传入 `personalUpdateOwner=poesein`，应用内更新检查 `poesein/Melodia` 的 Releases。未传此参数的构建仍使用原项目默认的官方更新源。
- 工作流的 artifact 只是构建下载文件，不会自动成为应用内可检测的 Release。个人仓库没有发布新 Release 时，应用不会因为官方仓库发布新版本而得到个人版更新。
- 本地生成个人 APK 不等于 GitHub 已配置签名 secrets 或已成功运行工作流；没有完成下面的配置时，不能认为云端已经能够自动生产个人安装包。

## 合并官方后续修改

先保存当前修改并确认工作目录干净。在仓库根目录执行：

```powershell
git status
git switch personal/local-first-search
git remote -v
```

若还没有 `upstream` 远程，只执行一次：

```powershell
git remote add upstream https://github.com/rinchao0721/Melodia.git
```

每次更新先从个人分支新建临时集成分支，再合并官方主分支。下面的分支名是示例，每次使用新的名字：

```powershell
git fetch upstream
git switch -c integrate/upstream-2026-10-15
git merge upstream/main
```

遇到冲突，检查双方修改并保留需要的个人功能，再 `git add` 已处理文件、`git commit` 完成合并；可用 `git merge --abort` 撤销尚未完成的这次合并。优先检查 `LocalMusicApi`、播放源解析、本地音频匹配、歌手分页、设置与 DI、曲库数据库、搜索 UI、APK 标识和更新源配置。按业务块合并，避免用个人旧文件整体覆盖官方新实现。

使用 JDK 21 和仓库 Gradle Wrapper，按官方 CI 运行：

```powershell
.\gradlew.bat :app:testDebugUnitTest :shared:desktopTest :desktopApp:test :desktopApp:compileKotlin :app:assembleRelease
```

上述命令验证默认配置。交付个人 APK 时还须传入个人包名、标签、更新仓库、递增版本号和原签名材料，并核验实际 APK；可沿用现有个人构建脚本或下方手动工作流。Release 构建含 R8，不等于完整 `lintRelease` 所有检查通过。

至少回归：旧关联覆盖升级、手动与自动音源优先级、文件失效回退、自动匹配暂停后继续、单条报告恢复、专辑人工确认后移入已完成并跨重启跳过、增加本地曲目后重新核验、专辑筛选全局与单歌手设置，以及搜索返回原音乐页。验证后将集成结果合回个人分支：

```powershell
git switch personal/local-first-search
git merge --ff-only integrate/upstream-2026-10-15
```

若个人分支期间又有新提交导致不能快进，先把这些提交合入集成分支并再次验证，再合回；不要用强制覆盖跳过冲突检查。

不要对个人功能分支执行 `reset --hard upstream/main`，也不要把网页 `Sync fork` 的强制丢弃提交选项用于覆盖个人功能。可以让 fork 的 `main` 单独跟随上游，但个人功能分支应通过 merge 接收更新。

## 在 GitHub 手动构建

将个人修改和工作流提交到 fork 后，在仓库 Settings → Secrets and variables → Actions 添加以下 Repository secrets：

| Secret | 内容 |
| --- | --- |
| `RELEASE_KEYSTORE_BASE64` | 同一个个人 keystore 的 Base64 内容 |
| `RELEASE_STORE_PASSWORD` | keystore 密码 |
| `RELEASE_KEY_ALIAS` | 个人签名密钥别名 |
| `RELEASE_KEY_PASSWORD` | 该别名的密钥密码 |

工作流须位于仓库默认分支，GitHub Actions 才会提供手动运行入口；可将这个工作流单独合入默认分支，再在 Run workflow 的分支下拉框选择个人功能分支。通过网页秘密输入框填写签名材料，不要把内容粘贴到 issue、聊天、日志或源码。

进入 Actions → Personal Android APK → Run workflow，选择包含个人修改的分支，输入 `version` 和 `version_code`。例如：

```text
version:      2.0.0-beta.12
version_code: 2000012
```

这是本次版本的格式示例；后续新包的输入必须高于已安装个人版，不能对新的修改重复使用 beta.12 版本码。工作流使用 JDK 21，执行 `:app:testDebugUnitTest` 和 `:app:assembleRelease`，并传入：

```text
-PpersonalApplicationId=com.lin0721.linmusic.personal
-PpersonalAppLabel=Melodia Personal
-PpersonalUpdateOwner=poesein
```

四项签名材料缺失、版本格式错误、APK 回退到 Android Debug 签名、APK 证书与提供的个人 keystore 不一致，或 APK 包名/版本不符时，工作流失败，不上传该 APK。成功后在该次运行的 Artifacts 下载个人 APK；混淆映射用于排查该版本崩溃，单元测试报告用于查看测试结果。

## 可选：发布个人 Release 供应用内检查

当前 `VersionCodeResolver` 只接受 `vMAJOR.MINOR.PATCH`、`vMAJOR.MINOR.PATCH-beta.N` 和 `vMAJOR.MINOR.PATCH-rc.N` 形式的 tag；`beta.N` 的 N 为 0–49，`rc.N` 为 0–48。不要使用 `-personal`、`-local` 等额外后缀，否则应用内更新会跳过该 Release。

版本码公式为：

```text
versionCode = (MAJOR × 10000 + MINOR × 100 + PATCH) × 100 + subCode

beta.N: subCode = N
rc.N:   subCode = 50 + N
正式版: subCode = 99
```

同一基本版本中 beta、rc、正式版依次递增。例如 `2.0.0-beta.3` 为 `2000003`、`2.0.0-rc.0` 为 `2000050`、`2.0.0` 为 `2000099`。工作流会校验输入版本码与公式相同。个人版本发布次数与官方版本命名需自行协调；发布同一版本名的改动必须提升到下一个有效版本，不能重复使用旧 versionCode。

如需应用内更新，在 `poesein/Melodia` 手动创建 Release，使用受支持且与 APK `versionName` 对应的 tag，并上传**使用个人配置构建、具有个人应用 ID 和同一签名且已经验证的 APK**。预发布 tag 在 GitHub 标为 Pre-release，并在应用中允许预发布更新。不要上传官方 APK 作为个人 Release 的安装资产。

原仓库仍带有 `Release` 工作流，匹配 `v*.*.*` 的新 tag 推送可能触发原版 Android 和桌面构建及发布；该工作流没有个人构建参数。首次手动创建个人 Release 前，可在 fork 的 Actions 页面禁用原 `Release` 工作流，或由你另外明确改造成个人发布流程，避免它发布或混入原版包。新增的个人工作流本身不会创建、推送 tag，也不会触发该发布流程。

仅发布 artifact、复制官方 Release 信息、发布草稿 Release，或上传无法被版本解析器识别的 tag，都不能保证应用内更新可见。每次发布后实际检查个人应用能否找到该 Release、下载的包名是否正确、签名是否相同及能否覆盖安装。
